# Tasks

This is the implementation plan for the Tapas Contest App. The ordering is deliberate: each task produces a runnable artifact that the next task depends on. There are no parallel tracks; the project is too small for that and the dependencies are too tight.

The project has **three AI surfaces**, each with its own eval set:

1. **Contest-creation LLM** — extracts `ContestDraft` from natural language. 25 cases.
2. **Host-assistant LLM** — picks MCP tools in response to host messages. 30+ cases.
3. **Infrastructure-generation AI** — produces Dockerfiles, CI pipeline, compose file. ~10 cases.

All three are governed by the same discipline: schema-validate the output, review it, version it, audit every action.

- [x] **2.3** Implement the LLMClient: function-calling adapter that takes a host message and returns a parsed `ContestDraft` shape (or partial + clarifications) — *Slice F1 done: `OpenAiCompatibleLLMClient` talks to any OpenAI-compatible `/chat/completions` endpoint (a local Ollama by default via `LLM_BASE_URL`/`LLM_API_KEY`/`LLM_MODEL`, or a hosted provider that mirrors the same API shape) — the real model lives only here and in the eval harnesses (design.md §11A.1); every test uses a `FakeLLMClient`/`StubLLMClient` with canned completions. `ExtractContestDraft` calls it with a system prompt + the `propose_contest_draft` tool (JSON schema, `additionalProperties:false` at every level — the security boundary), re-validates the tool-call output with Zod (two-phase validation, design.md §11B.2), and enforces the "may not default" allow-list (design.md §9) at the boundary — `attribution`/`antiBias`/`scoring`/`participants` tagged `source: "llm_default"` are stripped and replaced with a clarification, regardless of what the prompt asked for.*
- [x] **2.4** Implement the two-phase contest-creation flow: extract → clarify → finalize — *Slice F1 done (EXTRACT only): `POST /drafts/extract` (host-scoped, stateless) turns a free-form message into a partial draft with every field tagged `source: "host"|"llm_default"|"llm_extracted"`, plus a `clarifications` list. The host still saves via the existing `POST /drafts`. The CLARIFY phase (merging a follow-up host reply + prior partial draft into a more complete one) is deferred to Slice F2.*

  *Slice F2 done (CLARIFY/merge): `POST /drafts/merge` (host-scoped, stateless like extract) takes `{draft, clarifications, message}` — the prior partial draft, the questions still open, and the host's reply — and returns the same `{draft, clarifications}` shape as extract, so the chat can loop turn after turn until `clarifications` is empty. `MergeContestDraft` shows the model the prior draft and the open questions as context, then re-asks for the whole draft. **Merge rule: a field the model returns wins; a field it omits falls back to the prior draft.** The model is told to echo everything it knows, but a small local model that forgets to repeat a settled field must not silently erase it — carrying over is what makes multi-turn safe. For the same reason, a turn the model fails (no tool call, or unusable arguments) keeps the prior draft and its open clarifications and appends a "couldn't work that out" note, rather than resetting to `{}` the way extract does on turn 1 — by turn 2 there is progress to lose. The prior draft round-trips through the client, so it is untrusted: the route Zod-validates the whole body (`INVALID_MERGE_REQUEST`, 400) and the §9 "may not default" guard is re-applied to the **merged** result, which catches a high-stakes field forged as `llm_default` in the prior draft just as it catches one the model invents. Guarding the merged set once (rather than each side) is deliberate — guarding both halves asked the host the same question twice, caught in the live smoke test.*

  *Shared with F1 and hardened during F2 (`proposed-draft-guard.ts`): re-validation of a tool call is now **per field, not all-or-nothing**. The live smoke test against a real local Ollama (`gemma4:e4b`) showed the previous behavior discarding an entire good draft because one nested field came back malformed (`scoring.range: null`) — the host lost a correctly-extracted name and the model's own clarifications along with it. Now each field is validated against its own schema; one that fails is dropped and becomes a clarification naming it, and the rest survive. Fields the model reports as undetermined — `null`, or `{value: null, source}`, both of which real models emit constantly instead of omitting the key — are treated as simply absent rather than as unusable answers. Only known field names are ever read, so the `additionalProperties: false` tool schema stays the structural boundary and anything smuggled past it is dropped rather than propagated.*

  *Known local-model limitation, reported honestly (as in F1): `gemma4:e4b` reliably fills in name/attribution/antiBias/participants across the two turns, but repeatedly produced a malformed `scoring` config (null `range`), so the merged draft correctly kept asking for the scoring rules. That is the guard working as intended, not a code defect — but it is the kind of case task 3.2's "partial + clarify" eval cases exist to measure.*

## Phase 3 — Eval harness and prompt iteration (1 week)

Two AI surfaces get evaluated here: the contest-creation LLM (25 cases) and a *baseline* of the host-assistant LLM. The full host-assistant eval lands in Phase 4, after the MCP tools exist.

- [x] **3.1** Define the eval case schema: `input` (host message), `ground_truth` (expected draft or tool calls), `category` — *Slice G1. Lives in the new `@tapas/evals` workspace (`packages/evals`), which will hold all three eval sets. A case is `{id, category, note?, turns[]}`: **every case is a list of turns**, single-turn cases just have one. Turn 1 runs EXTRACT, turns 2+ run MERGE with the previous turn's draft + clarifications fed back — the original flat `input`/`ground_truth` shape could not express the "4 partial + clarify" cases at all once Slice F2 made them genuinely two-turn. Each turn expects `{fields, clarifiesAbout, absent}`. **Ground truth asserts values, not `source` tags** — whether a model calls something `host` or `llm_extracted` is subjective and would make cases brittle for no measurement gain. Cases are Zod-validated at load (`parseCases`), so a malformed case fails loudly instead of silently skewing a metric.*
- [x] **3.2** Author 25 contest-creation cases: 8 simple, 10 domain, 4 partial + clarify, 3 adversarial — *Slice G2. In `packages/evals/cases/creation/` split by category, with `index.ts` exporting the frozen `CREATION_CASES`. **Ground truth describes what a good assistant should do, not what today's local model manages** — the cases are a spec meant to outlive any one model, and where the current model falls short that belongs in the thresholds and trajectory (3.5/3.6), not in a weakened expectation. Every case carries a `note` saying why it exists. The **10 domain cases** are built on the rule space in glossary.md and include the three named variants (Strict = per_person/couples/auto/unique, Permissive = per_person/couples/1..10/repeats, Joint = per_couple/couples/1..10/repeats) — the same points the compiler's acceptance spec uses — plus auto-range described in the host's own words, arbitrary_pairs via `noScoreWith`, per_couple attribution deliberately worded so it must NOT be conflated with the couples anti-bias rule, uniqueness-as-ranking, categories inferred from prose, and scheduled close/reveal as separate axes. The **4 partial+clarify** cases are genuinely two-turn and test the F2 merge contract (carry-over, shrinking clarifications, and a reply that *corrects* an already-settled field). The **3 adversarial** cases test **containment, not refusal**: each also asserts the legitimate extraction still succeeded, because a case that only checked "the attacked field is unset" would pass just as well if the assistant fell over entirely.*

  *Structural guards on the set are deterministic and hard-gate (`tests/unit/creation-cases.test.ts`, 14 tests): the 25 total and the 8/10/4/3 split, unique ids, every case noted, partial+clarify actually multi-turn, every adversarial case naming the field it attacks via `absent`, no turn both expecting and forbidding the same field, and every rule-space axis covered across the domain cases. The model's behaviour is threshold-gated; the eval set being well-formed is an ordinary invariant.*

  *CLI gained `--category` / `--case` filters for authoring and for investigating a single regression (the case-set hash is always computed over the FULL set, so a filtered run can never be mistaken for a baseline), and per-case progress streaming — a 25-case run is tens of real model calls over many minutes, and reporting only at the end was indistinguishable from a hang.*

  *First observed baseline, `gemma4:e4b` @ temperature 0, seed 1, case-set `5db74e07d785` (NOT a committed threshold — that is 3.5/3.6): overall schema validity 27.6%, field accuracy 84.0%, missing-field recall 90.9%, false-field rate 1.9% (29 turns, 1 no-tool-call, 20 with a rejected field). By category — simple sv 37.5 / fa 100; domain sv 30 / fa 76.2; partial+clarify sv 12.5 / fa 80 / recall 100; adversarial sv 33.3 / fa 100 / recall 80 / false-field 16.7. **The dominant failure is malformed field objects, not wrong answers** — when a field survives re-validation it is usually right (fa 84–100), but the model frequently emits structurally invalid field wrappers that per-field validation drops. That points 3.6's prompt/tool work at the field shape, not at the extraction logic. The adversarial 16.7 false-field is the real signal: on `adversarial-instruction-disabling-anti-bias` the injected participant name DID set `antiBias: none` — the §9 guard only strips `llm_default`, and an injection arrives tagged `host`. Tracked as a separate hardening task; design.md §11B.3 already claims this defense, so code and design disagree there.*

  *Two things running the set caught that reasoning did not — the reason for running each batch live (task 3.3 lesson, again). (1) A real production defect: `OpenAiCompatibleLLMClient` had no request timeout, so the first full run hung indefinitely (12 min at 0% CPU, no output, no error) when the local model was unloaded mid-run. Fixed with an `AbortController` timeout (120s default) + typed `LLMTimeoutError` + 5 unit tests — this would pin a host's HTTP request too, not just an eval. (2) Known harness gap left for 3.6 on purpose: the report records WHICH field was rejected but not WHY (the Zod issue / offending value), which prompt iteration will want.*
- [x] **3.3** Implement the eval runner: takes cases + LLMClient, returns per-case results and aggregate metrics — *Slice G1. `runEval(cases, llmClient)` drives the **production use cases** (`ExtractContestDraft`/`MergeContestDraft`), not a reimplementation of the pipeline: what the host's client would get is what gets scored, prompts and guards included. A case that throws (transport error) is recorded as `error` on that case rather than failing the run. Metrics are accumulated as **counts, summed then divided**, never as a mean of per-turn ratios — otherwise a 1-turn case would outweigh a 3-turn case on the same evidence. Definitions: **schema validity** = turns with a usable tool call and no field rejected (the report also breaks out `noToolCall` vs `fieldRejected`, so the F2-era "one malformed nested field" failure stays visible rather than hiding inside one number); **field accuracy** = of expected fields that actually appeared, the fraction deep-equal to ground truth (fields that never arrived are a recall miss, not an accuracy miss — counting both would penalize one mistake twice); **missing-field recall** = of `clarifiesAbout`, the fraction actually asked about; **false-field rate** = fraction of produced fields that ground truth explicitly forbids via `absent`. A metric with an empty denominator reports 1, not 0/NaN, so a case that legitimately asserts nothing isn't scored as a failure.*

Known bias: unmatched wording under-credits the model, chosen deliberately as the safe direction for a regression metric.*
